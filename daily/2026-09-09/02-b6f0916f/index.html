HFresh：内存高效的向量搜索

HFresh 是 Weaviate 的基于磁盘的向量索引（vector index），适用于那些优先考虑更低内存占用而非峰值查询吞吐量的应用场景。这种取舍对于资源有限的小型应用以及超大规模数据集都很有用。例如，Weaviate Cloud 的免费层（Free Tier）就通过其 Cost Optimized 配置默认使用 HFresh。

理解 HNSW 在相似度搜索中的内存瓶颈

在快速寻找相似向量方面，HNSW（Hierarchical Navigable Small World，分层可导航小世界）已经成为事实上的黄金标准。它既快速又准确，但当数据集规模从百万级增长到十亿级向量时，HNSW 暴露出一个根本性的限制：它的图结构与向量缓存都需要常驻内存。

HNSW 是一个基于图的索引，它将向量组织成分层结构。在最上层，是一张稀疏的、带有远距离连接的图，用于帮助你快速导航到目标邻域。随着你逐层下降，图会变得越来越稠密，包含更多局部连接，最终在最底层把你引导到最相似的向量。

问题不在于 HNSW 是否优秀。它确实非常优秀。如果你需要尽可能低的延迟和最高的吞吐量，HNSW 很难被超越。但很多应用更看重较低的内存占用和更大的可扩展性，而非顶级的查询性能。

正是在这种场景下，基于磁盘的索引开始展现价值。如果能用一部分延迟换取更低的内存占用和更大的数据集规模，会怎样呢？

HFresh 登场

HFresh 是一个现代化的基于磁盘的向量索引，专为大规模场景下的高召回率（recall）、强更新性能以及可控的查询 I/O 而设计。它建立在 SPFresh 研究论文所提出的思想之上，并将设计改造为使用 Weaviate 中已经久经考验的组件。

从高层视角来看，HFresh 属于基于分区的向量索引（partition-based vector index）家族。它不像 HNSW 那样把每个向量与全局图中的邻居相连，而是把向量划分成许多小块区域，称为 postings（分区条目）。每个 posting 包含在向量空间中彼此邻近的向量，并以 LSM 存储（Log-Structured Merge store，日志结构合并存储）的形式存放在磁盘上。

为了让这种布局高效，HFresh 采用了"两阶段搜索"策略。

首先，一个紧凑的内存中的质心索引（centroid index）用于识别向量空间中与查询相关的区域；随后，只有对应的 postings 才从磁盘读取并进行细节搜索。通过将磁盘读取限制在数据集的一小部分上，HFresh 旨在让 I/O 保持有界、延迟可预测，即便数据集增长到数十亿规模也是如此。

这种结构在设计之初就考虑到要支持超大规模数据集，同时保持性能可预测。

无需重建也能保持"新鲜度"

SPFresh 背后的核心思想（也为 HFresh 所继承）是：大多数更新只影响向量空间中一个很小的局部区域。

在传统的基于分区的索引中，更新会不断累积，分区也可能逐渐漂移，最终不得不进行全量重建来恢复召回率和延迟，而在超大规模场景下，这一过程可能耗费数小时甚至数天。

SPFresh 证明这往往是没有必要的。在结构良好的分区索引中，插入或删除一个向量通常只影响向量空间中的一小块邻域。你不必重建一切，而是可以通过增量重平衡（incremental rebalancing），用一系列局部操作来维持索引质量。拆分过大的 posting、合并过小的 posting、在边界变化时重新分配向量，这些操作大部分在后台异步执行，在小的局部失衡累积成全局问题之前就持续不断地加以修复。最终得到的索引能随着时间推移保持新鲜、均衡，而无需经历破坏性的重建周期。

HFresh 如何基于 SPFresh 进行构建

HFresh 沿用了 SPFresh 的核心思想，并将其改造以适配 Weaviate 的架构。目标不是逐个组件地复现论文，而是保留这个设计真正有趣的部分：用局部维护代替重建、对查询 I/O 进行受控管理、在内存路由层与基于磁盘的 posting 之间做到清晰分离。在此基础上，我们做了一系列务实的取舍。我们没有引入全新的 ANN（Approximate Nearest Neighbor，近似最近邻）机制，而是复用了 Weaviate 中已经久经考验的组件，并把它们塑造成服务于这种新布局的形态。也就是说既保留其总体理念，又对部分组件进行了重新设计，以更好地匹配 Weaviate 在索引、过滤、压缩和更新方面的既有优势。

用 HNSW 作为质心索引

HFresh 一个重要的设计选择是使用 HNSW 作为质心索引，而非 SPTAG。

SPTAG 是微软在最初的 SPANN 设计中使用的 ANN 索引，也被沿用到了 SPFresh 中。它将一棵分区树与一个图相结合，使查询能够快速导航到最近的质心，再由质心定位到正确的 posting 列表。然而对 Weaviate 来说，HNSW 是更自然的选择：它本就已经能够非常好地承担这一角色。

HNSW 是 Weaviate 中使用最广泛的向量索引，也是整个系统中最久经考验的组件之一。我们对它在生产环境中、在各种工作负载和数据集规模下的表现都有深入的理解。在 HFresh 中复用 HNSW 来做质心搜索，使得我们可以直接建立在已经被验证过的基础设施之上，而不是引入一个全新的机制。

HNSW 也与质心索引实际承担的工作高度契合。在 HFresh 中，质心层负责把查询快速、准确地路由到正确的 posting。这就要求它保持紧凑、延迟低，并且能随着 posting 的演变支持频繁的更新。质心并非一成不变：拆分、合并和重新分配会持续重塑向量空间的划分方式，因此质心索引必须能够吸收大量插入和删除，而不需要昂贵的重建。

另一个优势是，质心索引本身也可以做量化。因为质心层仅用于识别向量空间中有潜力的区域，HFresh 可以对那些向量进行相对激进的压缩，从而在维持所需准确度的同时降低内存占用。事实上，HFresh 使用带 RQ8 的 HNSW，将质心的内存占用降低到原来的 1/4。

在这里使用 HNSW 还意味着 HNSW 的任何改进都能自动惠及 HFresh。一个很好的例子是 ACORN，它通过让图遍历在仅有一小部分数据匹配过滤器时更高效，从而改进过滤搜索。由于 HFresh 依赖 HNSW 作为质心层，这些改进并非孤立存在：它们同时也强化了 HFresh 的查询路径。

量化

HFresh 在两个地方使用了 Rotational Quantization（旋转量化），并采用两种不同的压缩等级。

原因在于搜索的两个阶段职责不同。质心索引负责把查询路由到正确的 posting，因此它需要足够的精度，以避免把查询送到向量空间中错误的区域。而 postings 负责生成候选集；它们的近似分数并非最终排序，因为 HFresh 之后会用原始未压缩向量对最佳候选进行重打分（rescoring）。

Rotational Quantization 的工作原理是：先将向量旋转到一个更易于压缩的表示形式，再缩减每个维度的精度。HFresh 使用：对质心使用 RQ8，将质心向量的内存占用减少到 1/4；对 posting 使用 RQ1，相较 32 位浮点，向量存储量最多减少到 1/32。

质心索引使用 RQ8

HFresh 搜索的第一阶段使用建立在质心之上的 HNSW 索引。这个内存中的索引负责识别哪些 posting 可能包含查询的最近邻。

HFresh 在这里使用 RQ8，是因为路由错误代价高昂。如果质心搜索漏掉了正确的区域，后面对 posting 的扫描可能就再也看不到真正的最近邻。RQ8 提供了一个很好的折中：在包含开销之前，它让质心向量的有效载荷缩减为约 1/4，同时保留了足以保证路由准确性的精度。

这一点之所以格外奏效，是因为质心索引远小于完整的向量数据集。HFresh 完全可以用更高精度的压缩格式保存质心，并且仍然让内存层保持紧凑。

posting 使用 RQ1

在 HFresh 选出最有希望的 posting 之后，它会对存储在这些 posting 内部的向量进行扫描。这一阶段的取舍有所不同。

posting 存放在磁盘上，因此它们的大小直接影响存储成本和查询 I/O。HFresh 使用 RQ1 来存储 posting 中的向量，每个维度只用 1 个比特表示。相较 32 位浮点向量，这相当于将向量存储量减少到最多 1/32。

这种激进的压缩让每个 posting 体积更小、读取成本更低。它也让第一阶段的距离计算足够快，从而可以扫描大量候选。

HFresh 并不依赖 RQ1 的分数给出最终排序结果。RQ1 仅用于构建候选集。随后，HFresh 会取出排名靠前候选对应的原始未压缩向量，在重打分阶段重新计算精确距离。这样既能控制磁盘读取量，又不牺牲最终排序的质量。

后台操作

HFresh 之所以能长期保持平衡而无需重建，是因为维护机制被直接内建在索引之中。它不会让失衡不断累积、再用一次大型离线作业全部修好，而是把维护拆解成一系列可以持续处理的小型后台任务。

在实践中，绝大多数前台写入都很简单：向量被快速追加，后续工作被推入后台队列。这些任务被持久化到专用的磁盘队列中，因此即便发生重启也能存活，并由调度器增量式地消化。

HFresh 把这些工作组织为三类主要的背景任务：split（拆分）、merge（合并）和 reassign（重新分配）。

Split（拆分）：当一个 posting 增长得过大时，HFresh 会对其进行拆分。它会加载该 posting，回收陈旧条目，利用 Balanced K-Means（均衡 K-Means）算法把其中的向量划分为两组，并生成两个新的质心来替换原来的质心。这能防止 posting 过度膨胀，膨胀会让磁盘读取变重，也会让路由变得不够精确。

Merge（合并）：另一种情况是 posting 变得过小。这可能发生在删除之后，也可能只是因为数据分布在自然演化。此时 HFresh 会寻找一个邻近的、能容纳较小 posting 而自身又不会变得过大的 posting。如果找到了合适的目标，它就会把两者合并，并移除多余的质心。这能避免索引碎片化成大量过小的 posting。

Reassign（重新分配）：在一次拆分或合并之后，一些向量可能已经不再属于它们当前所在的 posting。此时就需要重新分配。SPFresh 论文描述了一种名为 LIRE（Lightweight Incremental Rebalancing，轻量级增量重平衡）的协议：在拆分之后，检查是否有一些向量在新质心下、或者在某个邻近 posting 下会更合适；在合并之后，则检查被合并进来的某些向量是否其实应该被移到他处。这些重新分配让 HFresh 可以逐步修正错误，而不是试图一步到位把所有事情做对。

三类后台操作共同构成一个持续的平衡闭环：插入带来局部变化，索引则在后台悄悄收拾残局。最终得到的索引能够长期保持新鲜，而无需经历破坏性的重建周期。

过滤搜索

过滤向量搜索（filtered vector search）引入了额外约束：结果既要与查询向量相似，又要满足过滤条件。例如在电商搜索中，这可能意味着在指定品牌、价格区间内且有货的商品中找出相似产品。

HFresh 使用一个以位图（bitmap）表示的 allow list（允许列表）来追踪满足过滤条件的文档 ID。随后，它会根据匹配向量的数量在两种搜索策略之间做出选择。

对于高选择性的过滤器（highly selective filters），运行完整的 HFresh 流水线可能比直接在匹配子集上搜索更昂贵。当 allow list 包含的 ID 少于 5000 个时，HFresh 会绕过质心路由和 posting 扫描，直接取出这些 ID 对应的原始向量，并计算它们之间的精确距离。当前的 5000 ID 阈值是一个固定的内部启发式策略，既不可配置，也不是通用的调优建议。

基于 posting 的过滤

对于更宽泛的过滤器，HFresh 使用常规的两阶段搜索，并结合一种"感知 posting"的预过滤形式。过滤器识别出匹配的对象，而质心 HNSW 将查询路由到 posting 而非单个对象。HFresh 用一份记录了每个 posting 包含哪些向量 ID 的元数据，把这两层衔接起来。

流程如下：

- 利用 posting 元数据，把对象级别的 allow list 转换为 posting 级别的可用性。
- 在质心 HNSW 上借助 ACORN 进行导航，挑选出至少能贡献一个匹配向量的 posting。
- 读取被选中的 posting，在扫描其压缩向量的同时重新应用原始的 allow list。
- 使用原始未压缩向量，对排名靠前的候选进行重打分。

因为 HFresh 允许把同一个向量复制到多个 posting 中，它还会追踪哪些匹配向量已经为 posting 选择作出过贡献。这样就能避免仅仅因为多个 posting 包含同一匹配的副本就把它们都读出来。posting 级别的选择与向量级别的校验相结合，既减少了不必要的磁盘读取，又确保最终结果确实满足过滤条件。

如何使用 HFresh

要使用 HFresh，只需在创建集合（collection）时把它配置为向量索引。

下面是一个使用 Python 客户端的示例：

from weaviate.classes.config import Configure, VectorDistances

client.collections.create(
    name="Article",
    vector_config=Configure.Vectors.self_provided(
        name="Title",
        vector_index_config=Configure.VectorIndex.hfresh(
            distance_metric=VectorDistances.COSINE,
        ),
    ),
)

调优 HFresh

建议从默认值开始。如果召回率偏低，可以增大：

- search_probe：每次查询搜索更多 posting；
- quantizer.rescore_limit：使用全精度向量对更多候选进行重打分。

这两个设置都可以在无需重建索引的情况下修改。

实验

我们在 DBpedia OpenAI 1M 数据集上对未压缩的 HNSW、带 RQ1 的 HNSW、带 RQ8 的 HNSW 以及 HFresh 进行了基准测试。HNSW 索引构建时使用 efConstruction=256、maxConnections=16。

堆内存使用

以下测量的是 Go 堆（heap）使用，而非整个进程或系统内存。HFresh 还会依赖操作系统管理的页面缓存来访问磁盘上的数据，这部分并未被堆内存的统计数字所涵盖。

最直观的差异体现在空闲时的堆内存占用。HFresh 仅使用 239 MB 的堆，而未压缩的 HNSW 则需要 6.67 GB。

HFresh 的堆占用也低于量化版的 HNSW。带 RQ1 的 HNSW 使用 715 MB，大约是 HFresh 的 3 倍；带 RQ8 的 HNSW 使用 2.38 GB，大约是 HFresh 的 10 倍。

这一差异直接源自 HFresh 的架构。HFresh 把经 RQ8 压缩的质心索引和支撑元数据保留在内存中，而把压缩后的 posting 存放在磁盘上。posting 的成员关系、向量版本与删除状态，以及 posting 的大小同样会消耗堆内存，并随数据集增长，但这种布局显著降低了索引数据所需的堆内存。

查询吞吐量

QPS-recall 曲线展示了 HFresh 在堆内存优势之外的另一面：查询性能。

在相近的召回率下，HNSW 及其量化变体的吞吐量都显著高于 HFresh。这是意料之中的：HNSW 在内存图上搜索，而 HFresh 需要从磁盘读取选中的 posting，并取出原始向量进行重打分。

这些结果清晰地指明了何时该选择哪种索引。当最低延迟和最高吞吐量至关重要时，HNSW 仍是更好的选择。HFresh 则是为那些"无法负担把整个索引都放在内存中"的场景而设计的，在这些场景中，用较低的吞吐量换取小得多的堆内存占用是一种可接受的取舍。

结论

HFresh 为 Weaviate 提供了一种基于磁盘的索引，可用于从小型应用到大型可变数据集的内存高效向量搜索。通过把紧凑的质心索引和支撑元数据保留在内存中，同时以增量方式维护磁盘上的 posting，它既降低了索引数据所需的堆内存，又摆脱了对全量索引重建的依赖。当最低延迟和最高吞吐量至关重要时，HNSW 仍是更好的选择；而当更小的堆内存占用足以成为放弃部分查询吞吐量的理由时，HFresh 就是为此而设计的。

编辑导读

HFresh是Weaviate基于SPFresh思路打造的磁盘型向量索引，放弃HNSW全内存图结构，改用分区postings存于LSM存储。两阶段检索先由内存质心定位候选区，再按需读取磁盘分块，以可控I/O换取更低内存占用，并通过增量重平衡避免大规模重建。

为什么读为受内存预算约束的向量检索场景提供了一个HNSW之外的实用替代方案，并解释了背后的权衡。
