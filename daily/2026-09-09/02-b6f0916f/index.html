HFresh: 内存高效的向量搜索

HFresh 是 Weaviate 的基于磁盘的向量索引（disk-based vector index），适用于那些比起峰值查询吞吐量更看重低内存占用的场景。这种权衡在小资源的小型应用以及大型数据集上都很有用。比如 Weaviate Cloud 的免费版（Free Tier），默认就通过成本优化（Cost Optimized）配置跑的是 HFresh。

理解 HNSW 在相似性搜索中的内存瓶颈

要在大量向量里快速找出相似的，HNSW（分层可导航小世界图，Hierarchical Navigable Small World）已经是事实上的标准。它快，也很准。但当数据集从几百万向量一路膨胀到几十亿，HNSW 的一个根本性短板就暴露出来了，它的图（graph）和向量缓存都得待在内存里。

HNSW 是基于图的索引（graph-based index），把向量组织成分层结构。最顶层是一张稀疏图（sparse graph），节点之间距离拉得很长，方便你快速跳到大致正确的邻域。顺着层往下走，图越来越密，局部连接越来越多，最后在最底层把你带到最相似的几个向量跟前。

HNSW 好不好？好，没话说。要最低延迟和最高吞吐量，HNSW 很难被超越。但很多应用其实更看重低内存和大容量，而不是极致的查询性能。

这时候，基于磁盘的索引就值得看了。能不能拿一点延迟，换来大幅降低的内存占用，以及扩展到更大数据集的能力？

介绍 HFresh

HFresh 是一个现代化的基于磁盘的向量索引，目标是在大规模场景下做到高召回率（recall）、强更新性能，以及可控的查询 I/O。它建立在 SPFresh 这篇研究论文的思路之上，但把设计改造成直接复用 Weaviate 中已有且久经考验的组件。

从宏观上看，HFresh 属于基于分区的向量索引（partition-based vector indices）这一族。它不像 HNSW 把每个向量都连到一张全局图里，而是把向量切成很多小块，每一块叫一个分区（posting）。每个分区里的向量在向量空间上彼此靠近，整个分区作为 LSM 存储（LSM store）落到磁盘上。

为了让这种布局真正可用，HFresh 用了两阶段搜索策略。

第一阶段，内存里的紧凑质心索引（in-memory centroid index）先识别出查询相关的向量空间区域。第二阶段，只把这些相关分区从磁盘上拉下来做精细搜索。把磁盘读取限制在数据集的一小部分，HFresh 即使面对几十亿向量，也能让 I/O 受控、延迟可预测。

这套结构就是为了在支持超大数据集的同时，让性能保持稳定。

无需重建的「新鲜度」

SPFresh 背后的核心想法，也被 HFresh 继承了下来，其实很简单。大多数更新只影响向量空间里很小一片区域。

在传统的基于分区的索引里，更新会不断累积，分区也会慢慢漂移，最终不得不来一次完整重建（rebuild），才能把召回率和延迟救回来。这种重建在大规模场景下动辄几个小时甚至几天。

SPFresh 证明这事多半没必要。在一个结构合理的分区索引里，插入或删除一个向量通常只波及一小块邻域。靠一小组局部操作做增量再平衡（incremental rebalancing），就能维持索引质量，不用推倒重来。

具体三件事
- 拆分过大的分区
- 合并过小的分区
- 边界变化时重新分配向量这些操作大部分时间都在后台异步跑，持续地修复小的局部不平衡，不让它们攒成大问题。结果就是一个能长期保持新鲜和平衡的索引，没有那种折腾人的重建周期。

HFresh 如何在 SPFresh 的基础上构建

HFresh 把 SPFresh 的核心思想接过来，然后改造它来适配 Weaviate 的架构。目标不是把论文里的每个组件都复刻一遍，而是把其中真正有意思的部分留下来。

真正有意思的部分是这几样
- 用局部维护代替整体重建
- 可控的查询 I/O
- 内存路由层和磁盘分区层之间的清晰分离在这个基础上，我们做了一系列务实的选择。没有引入全新的 ANN（近似最近邻，Approximate Nearest Neighbor）机制，而是直接复用 Weaviate 里那些已经过验证的组件，把它们塑造成适配这种新布局的形态。SPFresh 的整体哲学保留下来，但部分组件重新思考了一遍，让它更贴合 Weaviate 在索引、过滤、压缩和更新上的既有优势。

用 HNSW 当质心索引

HFresh 里一个关键的设计选择是质心索引用 HNSW，而不是 SPTAG。

SPTAG 是微软最初 SPANN 设计里用的 ANN 索引，后来 SPFresh 也沿用了它。它把分区树和图结合起来，查询能快速导航到最近的质心，再从那里跳到正确的分区列表。但对 Weaviate 来说，HNSW 才是更自然的选择，它本来就已经把这件事干得很漂亮。

HNSW 是 Weaviate 里用得最多的向量索引，也是系统里最久经考验的部分之一。我们对它在各种工作负载、不同数据集规模下的生产行为，已经摸得很透。让 HFresh 复用它做质心搜索，可以直接站在已经验证过的基础设施上，不必再从零搞一套新机制。

HNSW 也恰好契合质心索引要干的活儿。在 HFresh 里，质心层的职责是把查询又快又准地路由到正确的分区。也就是说它必须保持紧凑、低延迟，并且能跟着分区的演化支持频繁更新。

质心不是静止的。拆分、合并、重新分配会一直重塑向量空间的分区结构，所以质心索引得能扛住大量插入和删除，不能动不动就要重建。

另一个好处是质心索引本身也可以被量化（quantized）。质心层只用来看向量空间里哪些区域有戏，HFresh 可以放心地把这些向量压得更狠，把内存降下来，同时不丢路由精度。实际上 HFresh 用的是带 RQ8 的 HNSW，把质心的内存占用压到了原来的四分之一。

这里用 HNSW 还意味着一个附加好处，对 HNSW 的改进会自动惠及 HFresh。一个典型例子是 ACORN，它通过让图遍历在只匹配部分数据集时更高效，从而改善过滤搜索。HFresh 的质心层就是 HNSW，所以这些改进不会被局限在一个孤立组件里，而是直接强化 HFresh 的查询路径。

量化

HFresh 在两处用到了旋转量化（Rotational Quantization），压缩等级还不一样。

原因在于这两阶段的活儿不同。质心索引负责把查询路由到正确的分区，精度必须够，否则查错方向代价就大了。分区则是用来生成候选集的，分区里的近似分数并不是最终排名，因为 HFresh 之后会用原始未压缩的向量对最佳候选项做重打分（rescoring）。

旋转量化的原理是这样的，先把向量旋转到一个更容易压缩的表示形式，再把每个维度的精度降下来。HFresh 的具体用法是这样

- 质心用 RQ8，质心向量的内存降到原来的四分之一
- 分区用 RQ1，相比 32 位浮点最多能把向量存储量压到三十二分之一

质心索引用 RQ8

HFresh 搜索的第一阶段是一个跑在质心上的 HNSW 索引。这个内存索引负责找出哪些分区最有可能装着查询的最近邻。

这里用 RQ8 是因为路由错不起。质心搜索一旦漏掉了正确的区域，后面的分区扫描可能永远也碰不到真正的最近邻。RQ8 是个不错的折中，在不算额外开销的前提下，把质心向量的载荷压到大约四分之一，同时保留住足够的精度来做准确路由。

这个选择能成立，一个重要原因是质心索引远小于完整向量数据集。HFresh 完全可以用更高精度的压缩格式给质心用，同时内存层依然紧凑。

分区用 RQ1

等 HFresh 选出了最值得看的几个分区，就开始扫描里面存的向量了。这一阶段的权衡又不一样。

分区在磁盘上，它们的大小直接决定存储成本和查询 I/O。HFresh 用 RQ1 来存分区里的向量，每个维度只用 1 个比特表示。相比 32 位浮点，向量存储量最多能省下 32 倍。

这么激进的压缩让每个分区都更小，读起来也更便宜。距离计算快到足以扫一大批候选项。

HFresh 不会拿 RQ1 的分数去定最终排名。RQ1 只负责搭起一个候选集。HFresh 再去拉这些头部候选的原始未压缩向量，在重打分（rescoring）阶段算精确距离。这样磁盘读取量压住了，最终排序质量也不掉。

后台操作

HFresh 能在没有重建的情况下长期保持平衡，是因为维护机制直接内嵌进了索引本身。它不会让不平衡攒到爆，然后来一次大修，而是把维护拆成可以持续消化的小后台任务。

实际跑起来，大多数前台写入都很轻。向量快速追加，后续工作扔进后台队列。这些任务持久化在专用的磁盘队列里，重启之后还在，调度器（scheduler）可以增量地慢慢抽干。

HFresh 把这些后台工作归成三大类，分别对应拆分（split）、合并（merge）和重新分配（reassign）。

拆分（Split） 当某个分区膨胀到太大的时候，HFresh 会把它拆开。系统先把分区加载进来，清掉过期条目，用 Balanced K-Means 算法把向量分成两拨均衡的小组，再生成两个新质心替换旧的那一个。这一步是为了不让分区无限变大，否则磁盘读取会越来越重，路由也会越来越不准。

合并（Merge） 反过来就是分区变得太小。删除会让分区变小，数据分布的自然演化也可能。遇到这种情况，HFresh 就去找一个邻近的分区，让它把这个小分区吃掉，又不至于自己长太胖。找到合适的候选就把两个合并，把多余的质心删掉。这一招能防止索引碎成一大堆小分区。

重新分配（Reassign） 拆分或合并之后，总有一些向量已经不再适合待在原来那个分区里。重新分配就是干这个的。SPFresh 论文里描述了一个叫 LIRE（轻量级增量再平衡，Lightweight Incremental Rebalancing）的协议。拆分后，它会检查是不是有些向量现在更适合归到某个新质心下面，甚至更适合去邻近的分区。合并后，它会检查那些被并进来的向量是不是其实该被搬到别处。这些重新分配让 HFresh 能逐步修正错误，不用试图一步到位做到完美。

这三类后台操作加在一起，就形成了一个持续的平衡循环。插入带来局部变化，索引在后台悄悄自我整理。最终就是一个能长期保持状态的索引，避开了那种伤筋动骨的重建周期。

过滤搜索

过滤型向量搜索（Filtered vector search）多加了一道约束，结果既要跟查询向量相似，又得满足过滤条件。拿电商搜索举个例子，可能就是要在特定品牌、特定价格区间、并且当前有库存的商品里找相似的。

HFresh 用一个位图（bitmap）形式的允许列表（allow list）来追踪满足过滤条件的文档 ID。然后根据匹配向量的数量，在两种搜索策略里挑一个。

当过滤条件很严格时，跑完整的 HFresh 流水线可能比直接搜匹配子集还贵。允许列表里的 ID 少于 5,000 个时，HFresh 就绕过质心路由和分区扫描，直接把这些 ID 对应的原始向量拉出来算精确距离。5,000 这个阈值目前是一个写死的内部启发式，不是可以调的参数，也不是通用调优建议。

感知分区的过滤

过滤条件更宽泛的时候，HFresh 就用常规的两阶段搜索，再叠一层感知分区的预过滤。过滤器负责识别匹配的对象，质心 HNSW 负责把查询路由到分区而不是单个对象。HFresh 用一份记录每个分区里有哪些向量 ID 的元数据，把这两个层级缝起来。

过程大致是这样第一步，用分区元数据把对象级的允许列表翻译成分区级的资格判定。

第二步，用 ACORN 导航质心 HNSW，挑出那些至少能贡献一个匹配向量的分区。

第三步，读取挑出来的分区，扫描它们压缩向量的时候再把原始允许列表过一遍。

第四步，用头部候选的原始未压缩向量做重打分。

HFresh 允许把同一个向量复制到多个分区，所以它还会跟踪哪些匹配向量已经对分区选择出过力，避免仅仅因为某些分区里存着同一匹配的副本就重复去读。分区级别的挑选加向量级别的核对，既减少了不必要的磁盘读取，又保证最终结果一定满足过滤条件。

如何使用 HFresh

要用 HFresh，创建集合（collection）的时候把它配成向量索引就行。

下面是 Python 客户端的示例

from weaviate.classes.config import Configure, VectorDistances

collection = client.collections.create(
    name="Article",
    vector_config=Configure.Vectors.self_provided(
        name="Title",
        vector_index_config=Configure.VectorIndex.hfresh(
            distance_metric=VectorDistances.COSINE,
        ),
    ),
)

调优 HFresh

先用默认值跑。召回率不够的话，调高下面这两个参数

- search_probe，让每次查询搜更多分区
- quantizer.rescore_limit，让更多候选用全精度向量重打分这两个参数都不用重建索引就能改。

实验

我们在 DBpedia OpenAI 1M 数据集上对比了未压缩的 HNSW、带 RQ1 的 HNSW、带 RQ8 的 HNSW，以及 HFresh。HNSW 索引用 efConstruction=256 和 maxConnections=16 构建。

堆内存占用

这些数字反映的是 Go 堆（heap）使用量，不是整个进程或者系统的内存。HFresh 还会用操作系统管理的缓存来管磁盘数据，这部分没被堆统计抓进去。

最直观的差异在空闲时的堆占用。HFresh 用 239 MB，未压缩 HNSW 用 6.67 GB。

HFresh 的堆占用也比量化的 HNSW 低。带 RQ1 的 HNSW 用 715 MB，大约是 HFresh 的 3 倍。带 RQ8 的 HNSW 用 2.38 GB，大约是 HFresh 的 10 倍。

这种差异直接来自 HFresh 的架构。它把 RQ8 压缩的质心索引和元数据留在内存里，把压缩后的分区放磁盘上。分区归属、向量版本与删除状态、分区大小这些也会吃堆内存，而且随数据集增长，但整体布局下索引数据需要的堆内存是显著降下来的。

查询吞吐量

QPS-recall 曲线把 HFresh 的堆优势在查询性能那一面也展示出来了。

召回率相当时，HNSW 和它的量化变体的吞吐量明显高于 HFresh。这不意外。HNSW 是在内存里的图上搜，HFresh 得从磁盘读分区，还得拉原始向量做重打分。

这些结果说明了两种索引什么时候该上场。要最低延迟和最高吞吐量，HNSW 还是更优。HFresh 是为这种场景准备的，把整个索引塞进内存代价太大，能接受吞吐量低一些，换来堆占用小很多。

除了 DBpedia 基准之外，我们还用十亿个随机生成的 256 维向量测了一下 HFresh 的索引构建。用的默认构建设置，12 个 worker，每批导入 1,000 条。

结论

HFresh 给 Weaviate 提供了一个基于磁盘的索引，让内存高效的向量搜索从小型应用一路覆盖到大规模可变数据集。紧凑的质心索引和支撑元数据留在内存里，磁盘上的分区以增量方式维护，索引数据需要的堆内存降了下来，全程不需要完整重建。最低延迟和最高吞吐量最重要时，HNSW 仍是更优选择。HFresh 是为愿意用查询吞吐量换堆占用的工作负载准备的。

编辑导读

Weaviate发布基于磁盘的向量索引HFresh，面向内存受限或超大规模场景，采用分区posting结构结合内存质心索引实现两阶段检索；通过增量拆分、合并与重分配避免整库重建，沿用SPFresh思路在高召回与可预测I/O之间取得平衡，并已成为免费层默认选项。
