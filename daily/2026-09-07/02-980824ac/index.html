用 100 步 GRPO 微调一个 350M 模型以获得更好的结构化输出

结构化输出是 LLM 最常见的现实任务之一，但大多数基准测试把它并入更广泛的推理或抽取分数中，而不是单独衡量它。一个模型是否能稳定返回符合请求格式与形状的、可解析的有效输出——即 schema 合规性（schema compliance）——往往决定了它能否被接入下游系统。

注意，这里描述的训练流程并不是用于训练 IFStruct 博客中所述 RL 模型的流程。本 notebook 并不旨在复现 IFStruct 基准分数，而是展示针对任务的微调如何提升小模型性能，并使其与更大的模型相匹配。

先决条件

本指南分为在两处运行的两部分：

微调（Fine-tuning） 在 GPU 上运行。配套 notebook 适配免费版的 Colab 或 Kaggle GPU。

评估（Evaluation） 可在 MacBook（本例中为搭载 Apple M5 Max 和 36 GB 统一内存的 MacBook Pro）上本地运行，通过 llama.cpp 暴露一个与 OpenAI 兼容的服务器，IFStruct 评估器会与之通信。

我们需要 uv 来管理 Python 工具链，并需要 llama.cpp 来提供推理服务。参考 Liquid AI 的 llama.cpp 部署文档，使用 Homebrew 安装 llama.cpp，并验证 llama-server 可用：

brew install llama.cpp
llama-server --version

在 LFM2.5-350M（基座模型）上进行 IFStruct 评估

在开始之前，我们先在 IFStruct 基准上评估 LFM2.5-350M，看看是否能复现报告的 21.1% 分数。

IFStruct 是一个用于测试 LLM 输出有效性与 schema 遵从度的基准。该基准在 Liquid4All/ifstruct 开源，公开的基准数据集在 Hugging Face 上的 LiquidAI/ifstruct-v1.0。

git clone https://github.com/Liquid4All/ifstruct.git

为了对比评估，我们在 MacBook 上用 llama.cpp 提供本地推理服务。我们将使用 BF16 版本的 GGUF（LiquidAI/LFM2.5-350M-GGUF）。

然后用如下命令启动基座模型服务器：

llama-server \
  -hf LiquidAI/LFM2.5-350M-GGUF:BF16 \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --alias LiquidAI/LFM2.5-350M \
  --host 127.0.0.1 \
  --port 8080

- --alias：IFStruct 发送给 OpenAI 兼容端点的模型名称
- -ngl 99：在 GPU 可用时，请求 llama.cpp 将所有层卸载到 GPU
- -np 4：并行处理 4 个请求
- -c 32768：提示上下文的大小

服务器运行后，我们就可以用 2000 条样本运行完整基准：

使用 TRL 对结构化输出进行 GRPO 微调

完整、可运行的流水线在配套 notebook 中。本节只涵盖其中的关键部分。

训练数据

我们使用 nvidia/Nemotron-RL-instruction_following-structured_outputs，它将每个提示与目标 JSON Schema 以及期望字段数量配对。我们使用约 500 条样本进行训练。

由于 Nemotron 数据分布与 IFStruct 评估不同，我们对提示做了增强，以弥合它们之间的两个差距：

- 40% 的提示追加了一条"将输出放在围栏代码块（fenced code block）内"的指令，让模型学会遵循格式指令，而不是总是直接输出原始 JSON。
- 另外不重合的 20% 被转换为顶层数组任务（schema 被包裹在一个 array 中，并要求一个 item 数量），用于训练裸列表（bare list）输出与 item 数量遵从。

模型与 LoRA

我们加载 LiquidAI/LFM2.5-350M 并附加一个 LoRA 适配器。由于 LFM2.5 采用混合注意力/卷积架构，我们针对 LFM 特定的模块名：

lora_config = LoraConfig(
    r=,
    lora_alpha=,
    bias="none",
    task_type="CAUSAL_LM",
    target_modules=[
        "q_proj",
        "k_proj",
        "v_proj",
        "out_proj",
        "in_proj",
        "w1",
        "w2",
        "w3",
    ],
)

这会训练约 6M 个参数，大约占模型的 1.66%。

奖励函数

然后我们定义三个奖励函数，每个都在 [0, 1] 区间内，根据所抽取的 structure（结构）是否正确对每个补全进行打分：

- json_format_reward：输出是否可解析，并采用所要求的格式？所要求的格式（围栏 vs. 原始）得满分 1.0；可解析但格式错误得 0.2；不可解析得 0.0。
- field_count_reward：对象是否具有期望数量的顶层字段？精确匹配得 1.0，分数随偏差线性衰减。
- schema_validation_reward：输出是否能通过该行对应的 JSON Schema 校验？它会统计每一条约束违反，并在必需键覆盖完整的前提下才发放部分奖励。

我们将三者以加权和方式组合，使用 reward_weights=[1.0, 0.5, 2.0]。

训练

我们训练 100 步，每个提示组采样 8 个生成，配置适配免费版 16 GB GPU：

from trl import GRPOConfig

training_args = GRPOConfig(

    gradient_accumulation_steps=,   # 每优化器步对应 4 个提示组
    steps_per_generation=,
    max_completion_length=,         # 为嵌套 JSON 留出空间
    mask_truncated_completions=False,
    temperature=1.1,                # 较高的采样温度以保持组内多样性
    beta=0.01,                      # 相对参考模型的 KL 惩罚

正如你在 notebook 中所看到的，整个训练过程中，三个奖励分量都在上升；与参考模型的 KL 在 warmup 后从零抬升；被截断补全的比例始终接近零。

合并并保存模型

最后，我们将 LoRA 适配器合并回基座权重，并保存为单一自包含的检查点（checkpoint），以便转换为 GGUF 用于推理服务：

MERGED_DIR = f"{training_args.output_dir}-merged"
merged_model = trainer.model.merge_and_unload()
merged_model.save_pretrained(MERGED_DIR)
tokenizer.save_pretrained(MERGED_DIR)

GRPO 微调后 LFM2.5-350M 的 IFStruct 评估

GRPO 微调完成后，我们重新运行 IFStruct 评估。为此，我们需要将合并后的模型检查点转换为 BF16 GGUF。转换脚本随 llama.cpp 源码一起提供，因此只需克隆一次仓库并安装其 gguf 包：

git clone --depth 1 https://github.com/ggml-org/llama.cpp
pip install ./llama.cpp/gguf-py

mkdir -p models

python llama.cpp/convert_hf_to_gguf.py \
  PATH_TO_YOUR_MERGED_MODEL \
  --outfile ./models/lfm25-350m-grpo-bf16.gguf \
  --outtype bf16

然后用如下命令启动合并后的模型服务：

llama-server \
  -m ./models/lfm25-350m-grpo-bf16.gguf \
  --alias lfm25-350m-grpo-structured-output \
  -c 32768 \
  -np 4 \
  -ngl 99 \
  --host 127.0.0.1 \
  --port 8081

接下来，我们使用微调后的模型再次运行完整的 IFStruct 评估：
