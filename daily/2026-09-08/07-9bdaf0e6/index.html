如何从 PDF 的图表里提取信息

如果你试过把一堆投资人 deck、科学论文或年报塞进 RAG（Retrieval-Augmented Generation，检索增强生成）管道，对这套流程一定不陌生。先跑一步 OCR（Optical Character Recognition，光学字符识别）或文本抽取，选个分块策略，把文本嵌进去，最后再检索。折腾完这一通，有人可能会问一个关于

过去大家只能这么干，把 PDF 里最有意思的部分统统跳过。比如带趋势的柱状图、对比表格、架构示意图，这些让 PDF 比纯文本更有价值的东西，全都进不了 RAG。

传统 RAG 为什么不够

先看看现在大家搭 PDF 的 RAG 管道时都在做什么。

对文件做 OCR 或文本抽取，Python 库或第三方工具都行。

把文本切成块。

用文本嵌入模型把分块向量化。

检索、可能再重排一下、然后生成。

这套流程本身没什么毛病，但它背后有个很天真的假设，页面可以被压扁成一串文本 token，内容的丰富度不会因此丢失。新闻稿或维基百科文章基本可以，但满满都是图表的 slide deck、带对比表格的 10-K、或者带说明图的学术论文，远远不够。

你也可以搭一套复杂的 ETL（Extract-Transform-Load，抽取-转换-加载）管道，把图表单独抽出来再向量化。但也就是说管道里又多一个模型，架构更复杂，查询时还得解决不同来源结果的合并问题。

用晚期交互多向量模型的话，这些都不需要。你嵌入的对象是整个页面，而不是页面里的文本。模型看图表的方式，跟你看图表的方式一模一样。没错，你没听错，连分块这一步都不存在。页面本身就是分块。

两段讲清晚期交互多向量检索

进入演示之前，先简单聊聊背后的原理。熟悉 ColPali 或 ColBERT 的可以直接跳过或扫一眼。

传统的稠密嵌入模型会把整个文档或分块压成单个向量。晚期交互多向量模型的做法不同，它把文档编码成一组向量，通常每个 token 一个。如果是视觉模型，比如我们马上要用的这个，则是每个图像块一个。查询时，查询本身也被编码成一组向量，相关性得分是查询 token 和文档 token 之间的最佳匹配之和，这个量叫 MaxSim。

模型不再问「这一整页是不是都在回答我整个问题」，而是问「这页里讲 Q4 FY26 的那部分，是不是跟我问题里讲『随时间变化』的那部分匹配得好」。对于图表密集的页面，这恰恰是合适的粒度。模型不必把整张 slide 压成一个向量，可以为页面上每个区域各保留一个向量，查询时挑出真正相关的那些区域。

所以这里其实有两个截然不同的优势。

因为是视觉模型，版面、图表、表格这些都保留下来了。

再加上对一组向量做 MaxSim，分块也就没必要了。

Weaviate 提供了一个叫 multi2multivec-weaviate 的向量化模块，在 Weaviate Cloud 上跑一个托管的晚期交互多向量模型。你不用自己托管或管理模型，就能从 PDF 生成多向量。

几点补充一下。

一个对象对应一页。 检索的最小单位就是页面，这也恰好是人浏览文档时的单位。

无需 OCR。 模型看到的从来不是「作为文本的文本」，而是把页面当作一张图像。正因如此，一张没标题的图表，它的可检索性跟一段文字是一样的。

向量被压缩过。 晚期交互模型每页可能产生几百个向量，原样存会很贵。Weaviate 用了一种多向量编码方案来压缩索引体积。更多细节放在下面的「权衡」一节。

用 Python 搭一条可部署的管道

拖拽 UI 是搭 POC（Proof of Concept，概念验证）最快的路径，但生产管道大多需要代码。下面是等价的约 50 行实现。

先装依赖。

pip install "weaviate-client>=4.21" PyMuPDF

然后把每个 PDF 页面渲染成长边 2000 像素的 PNG，作为 BLOB 存到用 multi2multivec-weaviate 向量化的 collection 里。

import os
from base64 import b64encode
from pathlib import Path

import fitz  # PyMuPDF
from weaviate import connect_to_weaviate_cloud
from weaviate.classes.config import Configure, DataType, Property


def page_to_b64(page, long_edge: int = 2000) -> str:
    scale = long_edge / max(page.rect.width, page.rect.height)
    pix = page.get_pixmap(matrix=fitz.Matrix(scale, scale))
    return b64encode(pix.tobytes(output="png")).decode()


client = connect_to_weaviate_cloud(
    os.environ["WEAVIATE_URL"],
    auth_credentials=os.environ["WEAVIATE_API_KEY"],
)

if not client.collections.exists("PDF"):
    client.collections.create(
        name="PDF",
        properties=[
            Property(name="pdf_name", data_type=DataType.TEXT),
            Property(name="page_number", data_type=DataType.INT),
            Property(name="page_image", data_type=DataType.BLOB),
        ],
        vector_config=Configure.MultiVectors.multi2vec_weaviate(
            image_field="page_image",
        ),
    )

col = client.collections.get("PDF")

for pdf_path in Path("pdfs").glob("*.pdf"):
    with col.batch.fixed_size(batch_size=2) as batch, fitz.open(pdf_path) as doc:
        for i, page in enumerate(doc, start=1):
            batch.add_object(
                properties={
                    "pdf_name": pdf_path.name,
                    "page_number": i,
                    "page_image": page_to_b64(page),
                }
            )

client.close()

关于上面代码的几点说明。

Python 调用 MultiVectors.multi2vec_weaviate(image_field="page_image") 配置的就是 multi2multivec-weaviate 模块。

跟控制台导入 UI 用的是同一个向量化器。

光栅化由 PyMuPDF 完成。2000 像素的长边目标是个合理的默认值，目标越小越省时间，越大则给模型越多细节。我们没找到低于 1500 或高于 2500 的强需求场景。

batch_size=2 是有意为之。每个对象都带一张好几 MB 的图像，小批量能让 gRPC 负载保持可控。

查询 collection 以返回排序后的页面。

from weaviate.classes.query import MetadataQuery

res = col.query.near_text(
    query="how did automotive revenue change over time",
    limit=3,
    return_properties=["pdf_name", "page_number"],
    return_metadata=MetadataQuery(distance=True),
)

for o in res.objects:
    print(o.metadata.distance, o.properties)

在 NVIDIA 语料上，这会把 Q2 FY26 的 Automotive 页作为第 1 条结果返回，就是你上面看到的那张三柱状图，由一条端到端、零 OCR 的管道检索出来。

response = agent.ask(

response.display()

那么这会是 PDF 的银弹吗

当然不会。工程领域永远都有取舍。

每个对象或页面包含大量向量。 晚期交互多向量模型每页会产生大量向量。你可以用 Muvera 这样的压缩技术部分抵消，Weaviate 原生支持。这确实有帮助，但也带来了压缩率与准确率之间的权衡。对于以海量纯文本为主的语料，比如法律合同、笔录或日志文件，文本嵌入模型仍然更便宜且足够准确。

页面级检索粒度偏粗。 如果答案藏在某份密集合同的一段话里，返回整页可能会塞给你过多无关上下文。实践中这一点通常能在智能体层缓解，比如 Weaviate 的 Query Agent，可以在不消耗大量 token 的前提下定位到相关段落。

模型必须能看懂你的图表。 它在公开训练语料上泛化得不错，但如果你有非常领域专属的视觉约定，比如高度风格化的内部模板，应当先在相应数据上验证一下检索质量。

那么晚期交互多向量模型什么时候能赢呢。主要在 PDF 密集型领域，比如季度 slide deck、尽调材料包、科学图表、技术图纸等等。对于以文本为主的语料，文本管道很可能更便宜且性能足够。

想进一步优化，可以考虑混合方案。把含图表的页面用多向量处理，其余语料用文本处理，再在查询时用类似 RRF（Reciprocal Rank Fusion，倒数排序融合）的方式合并结果。

小结

最后几条要点。

图表和表格不是 *靠更好的 OCR 就能解决的问题*。 它们是首要信息，在抽取过程中就被破坏了。如果你的管道只索引文本，图表里的宝贵信息在你开始嵌入之前就已经丢了。

晚期交互多向量模型让你彻底跳过抽取。 渲染页面、嵌入图像，直接问图像在表达什么。模型按页面「看起来的样子」来检索，图表、表格、版式，一个不落。

在 Weaviate Cloud 上，导入只需拖拽。 把 Query Agent 指向生成的 collection，提个问题，就能拿到带图片引用的答案。

把同样的原语封装成可部署的代码。 MultiVectors.multi2vec_weaviate(image_field="page_image") 就是全部的向量化器配置。剩下的就是用 PyMuPDF 渲染页面，外加一个不大的 batch.add_object 循环。
