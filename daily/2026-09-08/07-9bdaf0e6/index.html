如何从 PDF 中的图表里提取信息

如果你曾经试图把一堆投资者演示文稿、科学论文或年度报告放进 RAG（Retrieval-Augmented Generation，检索增强生成）流水线，你就会知道那套流程：先做 OCR（Optical Character Recognition，光学字符识别）或文本提取，选一种分块策略，嵌入文本，最后再检索。折腾完这些之后，可能有人问一个关于

Q2 FY25

营收的问题，而你的检索却返回三页毫不相关的要点，因为真正的答案在一张柱状图里，而索引根本看不到它。

过去人们只能这么做，把 PDF 中有趣的部分直接排除在 RAG 之外，比如带趋势的柱状图、对比表、架构图，以及那些让 PDF 比纯文本更有价值的内容。

本文将向你展示一种更好的方法：它不仅能检索到图表中嵌入的丰富信息，还能省掉繁杂的处理步骤。我们将涵盖：

经典 RAG：为什么 OCR 和文本嵌入对某些数据（结构化和非结构化）效果很好，但对富内容 PDF 却力不从心。

Late Interaction RAG：什么是 late-interaction 多元向量模型（late-interaction multi-vector model），以及为什么它能让你完全跳过文本提取。

真实示例：针对 NVIDIA FY2026 季度财报的查询示例，每个最相关结果都是能精确回答问题的图表本身。

传统 RAG 为何力不从心

先来看一下如今大多数人在为 PDF 构建 RAG 流水线时是怎么做的：

1. 对文件做 OCR（或文本提取）（使用 Python 库或第三方工具）。
2. 对文本进行分块（chunking）。
3. 用文本嵌入（embedding）模型对文本块做向量化。
4. 检索、（可选）重排（rerank）、生成。

这个流程本身并没有什么问题，但它有一个天真的底层假设：页面可以被简化为一系列文本词元（token），而不会丢失内容的丰富性。对于新闻稿或维基百科文章，这基本没问题；但对于满是图表的演示稿、含有对比表的 10-K 年报，或者带插图的学术论文，这样做远远不够。

你也可以搭建一套复杂的 ETL（Extract-Transform-Load，抽取-转换-加载）流水线来单独提取图表并做向量化，但也就是说流水线里又多一个模型，会引入更多复杂性，以及在查询时需要合并多种结果的问题。

而使用 late-interaction 多元向量模型，这些统统不需要：你嵌入（embed）的不是页面中的文本，而是整张页面。模型看到图表的方式和你一样。是的，你没听错，连分块这一步都没有，页面本身就是分块。

两段话讲清 late-interaction 多元向量检索

在进入演示之前，先简要介绍其背后的原理。如果你已经熟悉 ColPali / ColBERT，可以直接跳过或略读。

传统的稠密嵌入模型会把整个文档（或分块）压缩成单个向量。Late-interaction 多元向量模型的做法不同：它把文档编码为一组向量，通常每个词元对应一个向量（对于像我们即将用到的视觉模型，则是每个图像块 image patch 对应一个）。查询时，你的查询也被编码成一组向量，相关性得分是查询词元与文档词元之间最佳匹配的总和（这个量称为 MaxSim）。

模型不再问的是"这整页是否在讲我整个问题？"，而是可以问"这页里讲 Q4 FY26 的那一部分，是否与我问题中'变化趋势'那一部分匹配良好？"。对于满是图表的页面，这恰恰是所需的粒度。模型不必把整张幻灯片压缩成单个向量，而是可以为页面的每个区域各保留一个向量，查询时可以挑选出真正相关的区域。

所以这里实际上有两个明显的优势：

- 因为这是一个视觉模型，布局、图表、表格等都得以保留；
- 并且通过对一组向量使用 MaxSim，可以省去分块这一步。

Weaviate 提供了 multi2multivec-weaviate 向量化模块，它在 Weaviate Cloud 上运行托管的 late-interaction 多元向量模型，因此你不必自己托管或管理模型，也能从 PDF 生成多元向量。

通过拖拽导入 PDF

最快的试用方式就是 Weaviate Cloud 中的拖拽导入工具。

1. 在 Console 中打开你的集群。
2. 进入 Collections，创建一个新的集合。
3. 选择“从文件上传”选项，把 PDF 拖进去。

整个导入过程就这些。在后台，Weaviate 实际上做了三件事：

- 将每个 PDF 页面渲染为高分辨率图像。
- 将该图像作为 BLOB（二进制大对象）属性存储到一个新集合中。
- 用 multi2multivec-weaviate 模块对其进行向量化，为每页生成多个向量。

以下几点值得注意：

- 一个对象对应一页。 检索的最小单位就是页面，这恰好也是人阅读文档时的单位。
- 无需 OCR。 模型从不会把文本当作文本来看，而是把页面当作图像来看。这就是为什么一张没有标题的图表，与一段正文段落同样可被检索到。
- 向量经过了压缩。 Late-interaction 模型每页会生成数百个向量，若朴素存储成本会很高。Weaviate 使用一种多元向量编码方案来保持索引紧凑。（更多细节见后文权衡部分。）

在这个演示里，我们导入了 NVIDIA FY2026 四个季度的投资者演示稿（Q1 到 Q4）。它们覆盖截至 2026 年 1 月的财年，包含大量的图表和表格，一共 92 页。整个导入过程大约只花了一分半钟。

从搜索到答案：Weaviate Query Agent

向量搜索返回的是结果，但有时候你更想要一个答案。

Weaviate Query Agent 是一个托管的智能体，它把向量检索包装成多步推理、来源引用和内联页面图像。它开箱即用，适用于任何 Weaviate Cloud 集群。只需指向一个集合，然后提一个问题即可。

如果我们针对同一个集合问："FY26 各季度汽车业务营收如何变化？背后的驱动因素是什么？"，智能体会返回一个综合答案（柱状图中的数字，加上关于 Thor SoC 和 DRIVE AV 采用情况的要点），并把对应的页面图像作为引用。智能体自行决定检索哪些页面，视觉上"看"了它们，并直接从幻灯片中引用。

打开 Sources 面板，你就能看到答案背后具体引用了哪些页面。其中之一就是 Q1 FY26 演示稿中的 Automotive 页，也就是我们在原始向量搜索中浮现过的那种柱状图，只是来自不同的季度。

用 Python 构建可部署的流水线

拖拽 UI 是创建 POC（Proof of Concept，概念验证）最快的方式，但多数生产流水线都需要代码。下面就是等价的大约 50 行代码实现。

首先，安装依赖：

pip install "weaviate-client>=4.21" PyMuPDF

然后，把每个 PDF 页面渲染成长边 2000 像素的 PNG，作为 BLOB 存入用 multi2multivec-weaviate 向量化的集合中：

import os
from base64 import b64encode
from pathlib import Path

import fitz  # PyMuPDF
from weaviate import connect_to_weaviate_cloud
from weaviate.classes.config import Configure, DataType, Property


def page_to_b64(page, long_edge: int = 2000) -> str:
    scale = long_edge / max(page.rect.width, page.rect.height)
    pix = page.get_pixmap(matrix=fitz.Matrix(scale, scale))
    return b64encode(pix.tobytes(output="png")).decode()


client = connect_to_weaviate_cloud(
    os.environ["WEAVIATE_URL"],
    auth_credentials=os.environ["WEAVIATE_API_KEY"],
)

if not client.collections.exists("PDF"):
    client.collections.create(
        name="PDF",
        properties=[
            Property(name="pdf_name", data_type=DataType.TEXT),
            Property(name="page_number", data_type=DataType.INT),
            Property(name="page_image", data_type=DataType.BLOB),
        ],
        vector_config=Configure.MultiVectors.multi2vec_weaviate(
            image_field="page_image",
        ),
    )

col = client.collections.get("PDF")

for pdf_path in Path("pdfs").glob("*.pdf"):
    with col.batch.fixed_size(batch_size=2) as batch, fitz.open(pdf_path) as doc:
        for i, page in enumerate(doc, start=1):
            batch.add_object(
                properties={
                    "pdf_name": pdf_path.name,
                    "page_number": i,
                    "page_image": page_to_b64(page),
                }
            )

client.close()

关于上面的代码有几点说明：

- Python 调用 MultiVectors.multi2vec_weaviate(image_field="page_image") 配置了 multi2multivec-weaviate 模块。
- 这与 Console 导入 UI 使用的向量器是同一个。
- PyMuPDF 负责光栅化。
- 像素长边的目标值是一个合理的默认；目标值越小越省时间，越大则给模型提供更多细节。我们没有发现低于 1500 或高于 2500 的明显收益。
- batch_size=2 是有意为之。每个对象都承载着数 MB 的图像，因此小批量能让 gRPC 负载保持可控。

查询已创建的集合以返回排序后的页面：

from weaviate.classes.query import MetadataQuery

res = col.query.near_text(
    query="how did automotive revenue change over time",
    limit=3,
    return_properties=["pdf_name", "page_number"],
    return_metadata=MetadataQuery(distance=True),
)

for o in res.objects:
    print(o.metadata.distance, o.properties)

在 NVIDIA 数据集上，这会返回 Q2 FY26 的 Automotive 页作为第 1 个结果：也就是你在前面看到的那张五季度柱状图，由一个完全不需要 OCR 的端到端流水线检索得到。

你在 Console 中看到的同一个 Query Agent 也可以从 Python 调用。传入要进行推理的集合，然后调用 ask()：

from weaviate.agents.query import QueryAgent
from weaviate_agents.classes import QueryAgentCollectionConfig

agent = QueryAgent(
    client=client,
    collections=[QueryAgentCollectionConfig(name="PDF")],
)

response = agent.ask("How did automotive revenue change across FY26 quarters? What's driving it?")

response.display()

response.display() 会渲染出你在 Console 中看到的同样形式的综合答案，并附带页面图像作为引用。

那么这是处理 PDF 的银弹吗？

当然不是。正如工程中一贯的情况，这里存在权衡：

- 每个对象/页面对应大量向量。 Late-interaction 多元向量模型每页会生成许多向量。你可以通过 Weaviate 原生支持的压缩技术（如 Muvera）来部分缓解。这确实有用，但同时引入了压缩率与准确率之间的权衡。对于以大量纯文本为主的数据集（比如法律合同、笔录或日志文件），文本嵌入模型仍然更便宜，且准确度相当。
- 页面级检索粒度较粗。 如果你的答案藏在某份冗长合同里的某一段，返还整页可能会带来过多上下文。在实践中，我们通常在智能体层面来缓解这一问题（例如 Weaviate 的 Query Agent），它能在不消耗大量 token 的情况下定位到相关段落。
- 模型必须能"看懂"你的图表。 它从训练时使用的公开语料中能很好地泛化，但如果你的图表使用了非常领域化的视觉约定（例如高度风格化的内部模板），建议先在自家数据上验证检索质量。

那么 late-interaction 多元向量模型什么时候占优呢？主要在那些 PDF 密集、且包含季度演示稿、尽调材料包、科学图示、技术图纸等资产的领域。对于以文本为主的数据集，文本流水线很可能更便宜且表现足够好。

想要进一步优化，可以考虑混合方法：先用某种方式识别出包含图表的页面，用多元向量来检索；其余语料仍用文本，然后在查询时通过 RRF（Reciprocal Rank Fusion，倒数排名融合）之类的方式合并结果。

总结

最后用几条要点收尾：

- 图表不是靠更好的 OCR 就能解决的问题。 它们本身就是首要信息，会在抽取过程中被摧毁。如果你的流水线只索引文本，图表中的宝贵信息在你开始嵌入之前就已经丢失了。
- Late-interaction 多元向量模型让你完全跳过抽取。 渲染页面、嵌入图像，然后对图像的含义提问。模型按照页面的样子，图表、表格、布局等所有元素，来检索页面。
- 在 Weaviate Cloud 上，导入就是拖拽。 把 Query Agent 指向生成的集合，提个问题，就能得到带图像引用的答案。
- 把同一原语转化为可部署代码。 MultiVectors.multi2vec_weaviate(image_field="page_image") 就是全部的向量器配置。其余就是用 PyMuPDF 光栅化页面，再加一个小小的 batch.add_object 循环。
