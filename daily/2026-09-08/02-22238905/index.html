衡量 LLM 性能漂移：来自 31,352 次重复基准测试的观察与方法 [D]

关于 LLM 基准测试，有件事一直让我不太舒服。大多数基准其实就是一次性快照。模型跑一遍，分数出来，我们就拿着这个分数聊，仿佛它描述的是一个相当稳定的东西。

但 API 服务的模型不一样。模型名字背后那套东西会变。服务基础设施会变，提供商配置会变，版本号会变，有时候行为也变了，外面却看不到一次公开的版本切换。

所以我们换了个思路，把基准测试当成纵向测量（longitudinal measurement）问题，而不是去刷排行榜（leaderboard）。我们在编码、多轮推理、工具使用（tool use）这些任务上持续评估模型，同时高频跑一些轻量级的探针（probe）。

对我们来说，重点不是简单问一句「哪个模型分数最高？」。下面这些问题才是关键。

模型的行为和它自己之前的基线相比变了吗？变化幅度有没有超出正常的重复调用波动？基准配置本身动过没有？效果是不是集中在某个特定任务上？同一家提供商的几个模型之间有没有联动？看着像能力下降，到底是能力变了，还是只是可用性或者基础设施出了问题？

我们做过一次历史分析，覆盖 49 个模型，累计收集了 31,352 条重复观测的分数记录。日内分数的标准差是 2.80 分，日间每日中位数的标准差是 8.43 分。两者比值差不多是 1:3。

光凭这个结果，我没法下结论说提供商每天都在改模型。要这么说，混杂因素太多。任务构成、采样、缺失数据、提供商行为、方法论变化，哪个都有可能。但它至少说服了我们一件事，时间维度的变化值得专门去测，而不是被当成「永久排行榜分数」旁边的噪声。

所以我们现在这套做法，会给基准配置做版本管理，只在兼容的测量条件下做纵向比较。能用基于执行的评估（execution-based evaluation）的地方，我们就用，不依赖 LLM 评判（LLM judge）。可用性失败（availability failures）单独记，不和有效任务结果混在一起。提供商公开了服务或版本元数据（metadata）的，我们就抓下来。最后在时序数据上跑变化检测（change detection）。

另一个我们越来越关心的问题是识别度与污染（benchmark recognition and contamination）。一个基准一旦曝光度够了，你再把每道实时任务、提示变换、隐藏测试全放出来，你本来想测的东西就变了。所以我们试着把「方法论的透明」和「公开整套实时评估集」这两件事分开。现在我们已经把方法论的公开版写出来了。这份文档刻意把测量设计、假设、局限性、统计解读都讲清楚，但具体的实时任务库和一部分运营参数，留着不发。

我特别期待评估、变点检测（change-point detection）、生产环境机器学习方向的人来拍砖。我有几个问题，真心想听听大家的意见。

- 做纵向 LLM 评估，你会把每日中位数当作主要的时序单位，还是直接对每次重复观测建模？
- 版本元数据残缺的时候，怎么区分真实的模型漂移和提供商或者基础设施带来的影响？
- 一个实时基准，到底要藏多少才能既减少污染，又让方法论经得起审查？
- 这种非平稳（non-stationary）、噪声偏大的模型性能时序，有没有比变点检测器更合适的做法？
